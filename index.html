Brief Agent / Generator

The problem in one line Turn messy project context — rough notes, voice memos, half-formed asks — into a polished, Notion-ready creative brief through a guided conversation.

How to think about it

A brief isn't really a writing problem. It's a pulling-the-right-info-out-of-someone's-head problem. The content already exists somewhere — in rough notes, a voice memo, a Slack thread. Your job is to get it into a fixed shape (goal, audience, message, deliverables, timing, success metrics) and flag what's missing. The hard part isn't writing the brief. It's asking the right follow-up when an answer is too vague to be useful.

A suggested approach

  • Gemini as the interviewer. Give Gemini your brief template as its instructions and let it run a guided Q&A — ask one question, react to the answer, ask a smart follow-up. The trick: Gemini can take a long voice-memo transcript or a wall of Slack messages and pull out everything answerable before it even asks a question. The human only fills the gaps.
  • Glean for the "make it sound like our briefs" part. Glean already has your past briefs, brand guide, and messaging docs indexed. Once the agent has a rough goal and audience, ask Glean for similar past briefs and feed those back to Gemini as examples. This is what makes the output sound like your briefs, not a generic AI template.
  • Glean Agent to deliver it. Build the whole thing as a Glean agent. Glean's agent builder includes a write action that can post the finished brief straight into Slack (DM or channel) or create a Google Doc — no Zapier needed. If you specifically want Notion, that takes a custom Glean action against Notion's API, or just copy-paste. Don't burn time on delivery — the magic is in the interview.

Concrete first steps

  1. Write the brief schema down explicitly — every field, plus a one-line "what good looks like" for each. This single doc is the backbone of the whole agent.
  2. Build the Gemini interview loop with a hardcoded sample of messy input. Get the conversation feeling right before you add anything else.
  3. Add a "vague answer" check: have Gemini grade each field as specific / vague / missing, and refuse to finalize until the vague ones are addressed.
  4. Layer in Glean to pull past examples once the core loop feels good.
  5. Wire up delivery last — a Glean write action into Slack or Google Doc is cleanest. Save Notion for stretch.

Hints & gotchas

  • Resist the urge to ask all the questions upfront. The magic is in adaptive follow-ups — a good answer to "who's the audience" should change the next question.
  • Capture how much creative latitude the writer should have as its own field. That's the difference between a brief that helps and one that handcuffs.
  • Voice memos — don't over-build this. Gemini handles audio natively, or transcribe first. Either is fine.
  • Demo tip: show the same messy input going in and a clean Notion brief coming out, side by side. The contrast sells it.

Community Update Agent

The problem in one line Watch the #typeform-release Slack channel for product updates, then find community conversations where that news should be shared — keeping the community current and re-establishing Typeform as the source of truth.

How to think about it

This is a matching problem with two halves. First, spot a new release and figure out what it actually changes for users. Second, find community threads where that release answers an open question or fixes stale info. The second half is the interesting one — and it's not keyword matching. Someone asking "is there a way to do X" should match a release that adds X, even if they never use the same words.

A suggested approach

  • Gemini to read the release. Slack release notes are written for internal eyes. Have Gemini turn each one into a clean summary: what changed, who it affects, what user problems it now solves, plus a few paraphrased "questions this would answer." Those paraphrased questions become your search queries.
  • Glean to find the conversations. If your community platform is indexed in Glean, query it with those paraphrased questions. Glean is smart enough to surface threads where the customer asked the same thing in totally different words — that's the whole game. (If the community isn't in Glean yet, that's your very first decision — see gotchas.)
  • Run it as a scheduled Glean agent. Glean's scheduled triggers let an agent run automatically on a cadence (daily, weekly, whatever) in the background. So: scheduled agent → reads recent #typeform-release messages → runs the matching → posts results into a review channel using Glean's built-in Slack write action. The whole loop sits inside Glean, no Zapier required. (For the hackathon demo, you can also just trigger it manually when a release lands — keep the Slack-post step regardless, since that's what makes it feel real.)

Concrete first steps

  1. Pull 5–10 real past releases and, by hand, find the community threads each should have been shared in. This is your ground truth — you'll grade everything against it.
  2. Build the Gemini release-reader and check that its paraphrased questions actually resemble how customers ask things.
  3. Test Glean retrieval against your hand-labeled set: of the threads you found manually, how many does the agent surface?
  4. Wire up the Glean Slack write action to post matches to a review channel. Add the schedule (or trigger) last.

Hints & gotchas

  • Confirm the community is searchable in Glean first. If it isn't a Glean connector, you'll need to figure that out before anything else — settle it in hour one, it changes the whole build.
  • Keep a human approval step. Auto-posting into community threads is a reputation risk; the agent should recommend, a person should post.
  • Stale matches are a real failure mode — an old thread may already be resolved. Have Gemini double-check the thread's status before recommending.
  • Demo tip: take a real recent release and show the agent surfacing a real thread nobody had connected to it.

Content Engineering System

The problem in one line A centralized source of truth that dynamically feeds AI your brand guide, messaging docs, and content-type best practices — so contractors, agencies, and internal writers all work from the same inputs instead of material scattered across Figma, Notion, and Slides.

How to think about it

Content engineering basically means: make your brand context available to AI on demand, instead of relying on someone to remember which Notion doc the brand guide lives in and paste it into a prompt. The deliverable isn't a document. It's a system where "write a blog intro" automatically pulls in the right voice, the right rules for that content type, and the right examples — without the writer having to round any of it up.

This is the most behind-the-scenes of the five projects, which suits a small team. Less UI, more pipes.

A suggested approach

  • Glean as the source of truth. This is the heart of the project. Glean already indexes Notion, Slides, Drive, and Figma — so instead of moving all the scattered brand material, you make it findable in place. The win is that you don't have to migrate anything; you just curate what Glean indexes and how it's tagged.
  • A Glean Agent per content type. Build a separate agent for blog, exec comms, social, and so on. Each one knows which docs are authoritative for that content type and pulls them on demand.
  • Gemini as the writing layer. When a writer asks for a draft, Gemini gets the brand context plus content-type rules as background, then writes. Long context means you can hand it the full brand guide rather than a stripped-down summary.
  • A scheduled Glean agent for freshness. Glean's scheduled triggers can run a "check the source docs" agent weekly or monthly and post into a Slack channel when something looks like it's drifting — fully native to Glean, no Zapier needed. If you don't want to set up scheduling, a manual quarterly review works fine too.

Concrete first steps

  1. Inventory the scattered material: every brand guide, messaging doc, and best-practice file, and where it lives. Where versions conflict, decide which is the real one. This curation is the actual work.
  2. Confirm what Glean already indexes, and fill the gaps.
  3. Build one content-type agent end to end (blog is a good first pick) before generalizing.
  4. Define the rule: given a content-type request, what exactly gets pulled in, and in what priority order.

Hints & gotchas

  • The hard part is curating, not building. Conflicting and outdated docs are the enemy — a system that confidently pulls the wrong brand guide is worse than no system.
  • Don't try to cover every content type during the hackathon. One excellent agent beats six mediocre ones.
  • Be explicit about who owns each source doc. A "source of truth" with no owner goes stale immediately.
  • Demo tip: show the same content request answered by plain Gemini vs. your Glean-grounded version, side by side. The on-brand difference is the pitch.

Customer Journey 360

The problem in one line A unified view of everything a single customer receives across Iterable, Salesloft, Zendesk, in-app messages, and other touchpoints — so field teams can prep for calls and QBRs, investigate self-serve behavior, spot duplicate comms, and audit self-serve-to-sales handoffs using real examples instead of theory.

How to think about it

This is a stitching-together problem. Each tool only sees one slice of what a customer experienced; the value is putting it all on one timeline for one customer. Nail the timeline view for one customer before worrying about scale or polish.

A suggested approach

  • Glean for the qualitative layer. Glean already indexes Zendesk tickets, internal Slack discussion, and account notes — so for any customer, you can ask "what do we know about them?" and get the context the event logs don't carry. This is the layer that explains the why behind what happened.
  • Gemini to build the narrative. Feed Gemini the combined, timestamped events and have it produce: a clean chronological timeline, a plain-English summary ("here's what this customer has been through in the last 60 days"), and flags for duplicate or conflicting messages. Gemini's long context can handle a busy customer's full history in one pass.
  • Pulling the touchpoint data. Glean already indexes Zendesk and Slack, so those come for free. For Iterable, Salesloft, and other tools that aren't Glean-native, the cleanest hackathon path is a hand export for one customer into a Google Sheet. Zapier can automate it if you have access — but don't sink time there until you've seen what the data looks like.
  • Output. A prep doc a CSM can read before a call. Build it as a Glean agent and use the Google Doc or Slack write action — Glean will drop the summary into Drive or post it to a channel for you, no extra glue required.

Concrete first steps

  1. Pick one real customer with a rich, messy history — a good demo subject.
  2. Pull recent event data for that customer from each tool by hand. Don't automate collection until you know what the data looks like.
  3. Define a common event shape: timestamp, channel, type, summary. Normalizing into this shape is the core work.
  4. Build the Gemini timeline + duplicate-detection step.
  5. Automate collection last, only if there's time (Zapier optional).

Hints & gotchas

  • Timestamp normalization across five tools (time zones, formats) is the unglamorous part that will eat time. Budget for it.
  • "Duplicate comms" detection is a high-value, demoable feature — two tools emailing the same customer the same week is exactly the kind of finding that lands.
  • Don't try to integrate every touchpoint. Three tools, done well, beats five half-wired.
  • Demo tip: show one real customer's timeline and point to a genuine duplicate or a rough handoff. Concrete beats abstract.
  • Privacy: pick an internal-friendly account and don't surface anything sensitive in a shared demo.

Update Mega Mind

The problem in one line A system fed with project tooling, experiment updates, and status updates that can be queried to auto-generate recurring WBR, MBR, and other status decks — eliminating the repetitive deck-building that's currently eating into evenings.

How to think about it

Two distinct jobs here, and it helps to separate them: (1) gather and summarize what happened this week or month, and (2) render it into the recurring deck format. Almost all the value and almost all the difficulty is in job 1 — pulling scattered updates into an accurate, well-summarized status. Job 2 is templating.

Scope tip: a WBR content doc that's accurate and complete is a huge win on its own. A fully formatted slide deck is a stretch goal, not the starting point.

A suggested approach

  • Glean to gather the inputs. Project status, experiment updates, and tooling notes live across Notion, Slack, Jira, docs. Glean already indexes those — so the system can ask "what changed on Project X this week?" rather than you wiring up each source by hand.
  • Gemini to write it up. Feed Gemini the retrieved updates plus the structure of your WBR/MBR (sections, metrics, narrative style). Have it produce the status section by section. Long context lets you pass a whole week of raw updates at once. Hand it last cycle's deck as a style guide so the output matches house format.
  • Glean's scheduled triggers for cadence + delivery. This is exactly what Glean's scheduled-agent feature was built for. Set up a Glean agent that runs every Monday (WBR) or month-start (MBR), pulls the right updates via Glean's index, hands them to Gemini to write, and then posts the result to Slack or drops it into a Google Doc using a built-in write action. No Zapier required, no separate cron. Two things to know: scheduled Glean agents need at least one write action attached (the Slack post or doc creation counts), and your admin has to have scheduling enabled (it's off by default).
  • Slide rendering (stretch). Treat slide formatting as the last mile. A correct doc beats a pretty deck. Tackle slides only if everything else feels solid.

Concrete first steps

  1. Collect 2–3 past WBRs/MBRs and reverse-engineer the template: exact sections, what data each needs, the tone.
  2. List every input source a human currently checks to build the deck — that list is your Glean retrieval scope.
  3. Build the Gemini synthesis step on one past period and compare its output to the deck a human actually produced. Tune until close.
  4. Wire it up as a scheduled Glean agent with a Slack or Google Doc write action.
  5. Tackle slide formatting only if 1–4 are solid.

Hints & gotchas

  • Accuracy beats formatting every time. A perfectly styled deck with a wrong metric is worse than a plain doc that's correct. Have the system cite where each claim came from.
  • The system can't invent updates that weren't written down — part of the pitch is that it gently surfaces "Project Y had no updates this week," which is itself useful signal.
  • Don't sink the hackathon into pixel-perfect slides. Get the synthesis excellent; render simply.
  • Demo tip: generate this week's actual WBR live and let the team compare it to what they'd have written by hand.
